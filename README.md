# Домашние рецепты

Небольшая закрытая семейная книга рецептов с подробными шагами, фотографиями и списком ингредиентов. Для каждого ингредиента формируется безопасная поисковая ссылка на Яндекс Лавку; сайт не хранит cookies или данные аккаунта Яндекса.

## Возможности

- общая коллекция рецептов для нескольких пользователей;
- обложка блюда и фотография каждого шага;
- произвольные единицы измерения и примечания к ингредиентам;
- пересчёт количества ингредиентов под число порций;
- отдельный поисковый запрос для Лавки;
- чек-лист продуктов, копирование списка и резервные ссылки на поиск;
- фоновая сборка всей корзины в Ашане, Перекрёстке, Пятёрочке, Магните или Яндекс Лавке;
- настраиваемый приоритет магазинов и отдельная маркировка сомнительных замен;
- импорт по ссылке на сайт или YouTube с созданием проверяемого черновика;
- фоновая очередь импорта без отдельного Redis;
- закрытая регистрация: первый пользователь создаётся на `/setup/`, остальных добавляет администратор;
- тёмная тема по умолчанию с переключателем на светлую и локальными шрифтами без внешних CDN;
- PostgreSQL, Docker health checks и хранение изображений на отдельном volume.

## Локальный запуск

```bash
cp .env.example .env
# Заменить SECRET_KEY и POSTGRES_PASSWORD в .env
docker compose up --build
```

Открыть `http://localhost:30111/` и создать владельца. Для проверки кода:

```bash
./scripts/check.sh
```

### AI-импорт

Импорт всегда проходит через черновик: страница или субтитры извлекаются без участия модели, затем AI получает только очищенный текст и возвращает структурированный рецепт. Для страниц с корректной Schema.org `Recipe`-разметкой есть резервный детерминированный импорт без AI. YouTube требует доступных русских, украинских или английских субтитров; распознавание аудио без субтитров пока не выполняется.

Поддерживается любой доверенный OpenAI-совместимый endpoint. Настройки находятся в `.env`:

```dotenv
RECIPE_AI_BASE_URL=http://provider:8642/v1
RECIPE_AI_API_KEY=secret
RECIPE_AI_MODEL=recipes-importer
```

Для существующего Hermes на Raspberry Pi предусмотрена настройка:

```bash
./scripts/connect-hermes-pi.sh
```

Скрипт создаёт отдельный профиль `recipesimport` на модели `gpt-5.6-sol`, включает его API на `pi:8650`, задаёт отдельный bearer-токен и явно отключает все toolsets. Основной профиль Hermes и его модель не меняются. Это важно: обычный Hermes API без такой настройки является полноценным агентом и способен запускать инструменты на Raspberry Pi. Секрет передаётся напрямую в серверный `.env` TrueNAS и не сохраняется в репозитории.

### Автосборка корзины

Корзины собирает другой изолированный профиль Hermes: он имеет только браузерные инструменты, отдельный API-токен и постоянный браузерный профиль. АШАН, Перекрёсток, Пятёрочка, Магнит и Лавка выбираются в едином разделе «Магазины» Яндекс Еды с учётом сохранённого адреса. Недоступная по адресу сеть пропускается. Агент за один проход ищет товар, рассчитывает число упаковок и сразу добавляет их, но ему запрещено переходить к оформлению, подтверждать заказ или оплату.

Каждая попытка хранит журнал только реально добавленных упаковок. Если недоступно не менее 25% списка (минимум две позиции), эти добавления удаляются сразу. Готовая корзина ждёт подтверждения пользователя 180 минут (`CART_CONFIRMATION_MINUTES`), после чего worker удаляет только товары текущей попытки. Прежнее содержимое корзины не уменьшается.

Настроить профиль на Raspberry Pi и передать его токен в TrueNAS:

```bash
./scripts/connect-hermes-cart-pi.sh
```

Скрипт устанавливает Camofox (Camoufox/Firefox с устойчивым браузерным отпечатком), задаёт согласованные с российским IP локаль `ru-RU` и часовой пояс `Europe/Moscow`, поднимает отдельный виртуальный дисплей и профиль `recipecart` на `pi:8651`. Состояние входа хранится только на Raspberry Pi в закрытом каталоге профиля.

Для каждого пользователя сайта создаётся отдельный постоянный браузерный профиль: аккаунт Яндекса, адрес, cookies и корзина между пользователями не смешиваются. ID пользователя указан на странице корзины, когда требуется вход. Для первого входа пользователя с ID `1` запустите браузер, затем откройте его локальную панель через SSH-туннель:

```bash
./scripts/cart-browser-login-pi.sh start 1
ssh -N -L 6080:127.0.0.1:6080 pi
```

Откройте `http://127.0.0.1:6080/vnc.html`, авторизуйтесь и выберите адрес доставки. После этого остановите ручную сессию, чтобы сохранить профиль и освободить его для worker:

```bash
./scripts/cart-browser-login-pi.sh stop 1
```

Авторизация и адрес сохраняются в профиле этого пользователя для всех магазинов Яндекс Еды. Для другого пользователя повторите команды с его ID; одновременно открывайте для ручного входа только один профиль, поскольку панель noVNC общая.

Camofox и noVNC слушают только loopback-интерфейс Pi. Не пробрасывайте порты 6080, 5900 или 9377 на роутере и не публикуйте их через reverse proxy. Лучше использовать отдельный аккаунт магазина без сохранённых способов оплаты. Сайты применяют антибот-защиту, поэтому отдельные попытки могут потребовать CAPTCHA или повторного ручного входа; приложение показывает это как отдельный статус, а не как готовую корзину.

## Оформление

Все цвета живут в CSS-переменных `recipes/static/recipes/app.css`: блок `:root` описывает тёмную тему (она по умолчанию), блок `[data-theme="light"]` — светлую. Новые стили берут цвета только из переменных, иначе элемент сломается в одной из тем.

Выбранная тема хранится в `localStorage` под ключом `theme`. Переключатель — в шапке, а начальное значение `data-theme` выставляет инлайн-скрипт в `base.html` до первой отрисовки, чтобы тёмная тема не моргала светлой.

Шрифты — Inter (интерфейс) и Literata (заголовки), лежат в `recipes/static/recipes/fonts/` как переменные woff2 и подключены через `@font-face`. Запросов к внешним CDN нет. Начертания задаются переменными `--font-sans` и `--font-display`.

Иконки вкладки и приложения собираются из `recipes/static/recipes/icon.svg`:

```bash
cd recipes/static/recipes
rsvg-convert -w 512 -h 512 icon.svg -o icon-512.png
rsvg-convert -w 192 -h 192 icon.svg -o icon-192.png
rsvg-convert -w 180 -h 180 icon.svg -o apple-touch-icon.png
for size in 16 32 48; do rsvg-convert -w $size -h $size icon.svg -o /tmp/icon-$size.png; done
magick /tmp/icon-16.png /tmp/icon-32.png /tmp/icon-48.png favicon.ico
```

## TrueNAS SCALE

Конфигурация рассчитана на домашний сервер `truenas` по адресу `192.168.31.2` и порт `30111`.

```bash
./scripts/deploy-truenas.sh
```

Скрипт:

1. создаёт datasets `main-pool/config/recipes/{data,postgres}`;
2. генерирует секреты только на сервере в `/mnt/main-pool/config/recipes/.env`;
3. собирает локальный Docker image на TrueNAS;
4. регистрирует приложение как TrueNAS Custom App;
5. проверяет `/healthz/`.

Контейнер `worker` обрабатывает очередь импорта, а `cart-worker` — по одной браузерной сборке за раз. Если AI-провайдер находится на другом хосте, TrueNAS должен иметь к нему сетевой доступ.

### Автоматический деплой из GitHub

Workflow `.github/workflows/deploy.yml` проверяет каждый PR. После merge в `main` он собирает amd64-образ, публикует две метки в GHCR (`sha-<commit>` и `main`) и с Raspberry Pi обновляет TrueNAS Custom App на неизменяемую sha-метку. Runtime-секреты остаются только в `/mnt/main-pool/config/recipes/.env`; GitHub их не получает.

Однократная настройка runner и repository variables:

```bash
./scripts/setup-actions-runner-pi.sh
gh variable set DEPLOY_SSH_TARGET --repo pechatov/recipes --body nas
gh variable set RECIPES_APP_ROOT --repo pechatov/recipes --body /mnt/main-pool/config/recipes
```

Runner регистрируется только для `pechatov/recipes` и получает отдельную метку `recipes-truenas-deploy`. Deploy job запускается на нём только для `main`; проверки pull request выполняются на GitHub-hosted runner. На TrueNAS workflow передаёт стандартный короткоживущий `GITHUB_TOKEN` только в `docker login --password-stdin`, использует отдельный временный Docker config и удаляет его сразу после pull.

### Добавление второго пользователя

Владелец открывает `/admin/auth/user/add/`, создаёт пользователя и сообщает ему пароль безопасным способом. Обычному семейному пользователю права персонала не нужны.

### Резервное копирование

Создать согласованный дамп базы и рекурсивный ZFS snapshot:

```bash
./scripts/backup-truenas.sh
```

В резервную копию должны входить:

- дамп PostgreSQL базы `recipes`;
- dataset `main-pool/config/recipes/data` с фотографиями;
- закрытый файл `/mnt/main-pool/config/recipes/.env`.

Скрипт сохраняет `pg_dump` в dataset `main-pool/config/recipes/backups` и делает snapshot дерева `main-pool/config/recipes`. Это защищает от случайного удаления, но не от отказа всего пула; для полноценной резервной копии нужна репликация на другой носитель. Не публикуйте `.env` в Git.

### Reverse proxy и HTTPS

Приложение публикуется через существующий Nginx Proxy Manager по двум адресам:

- `https://recipes.pechatov.com`;
- `https://gotovka.pechatov.com`.

Runtime-файл `/mnt/main-pool/config/recipes/.env` должен содержать оба имени в `ALLOWED_HOSTS`, оба HTTPS origin в `CSRF_TRUSTED_ORIGINS` и `COOKIE_SECURE=true`. `SECURE_SSL_REDIRECT` остаётся выключенным: редирект и HSTS выполняет Nginx Proxy Manager, а локальный `/healthz/` остаётся доступен приложению по HTTP.

Идемпотентная настройка proxy host использует существующий wildcard-сертификат `*.pechatov.com` и сохраняет резервную копию базы NPM перед изменением:

```bash
ssh truenas "sudo env \
  NPM_DATA_DIR=/mnt/main-pool/config/nginx/data \
  RECIPES_CERTIFICATE_ID=2 \
  bash -s" < scripts/deploy/configure-npm-proxy.sh
```

По умолчанию оба домена проксируются на `192.168.31.2:30111`, HTTP принудительно перенаправляется на HTTPS, а конфигурация Nginx проверяется перед reload.
